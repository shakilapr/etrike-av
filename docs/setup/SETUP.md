# SETUP.md — AV Project Development Environment

## Project overview

This is a full-source Autoware development workspace for autonomous vehicle research. We keep the **entire Autoware source checked out on Linux**, mount it into a Docker container that provides the toolchain (Ubuntu, ROS 2, CUDA, compilers, dependencies), and build only the packages we modify with `colcon`.

**Key principle:** Docker provides the toolchain only. We do not bake source into the image or rebuild it on every change.

## How Docker fits in

```
              OUR LINUX FILESYSTEM
                       │
           ~/av_project/autoware
                       │
                       ▼
          ┌────────────────────────┐
          │ Docker development env │
          │                        │
          │ Ubuntu                 │
          │ ROS 2                  │
          │ CUDA                   │
          │ compilers              │
          │ dependencies           │
          │ colcon                 │
          │                        │
          │ /workspace/autoware ───────────┐
          └────────────────────────┘        │
                                            │
                                      bind mount
                                            │
                                      SAME FILES
```

- We **never make changes inside the Docker image.**
- We edit `~/av_project/autoware/src/...` on the host.
- Docker sees those exact files via bind mount.
- Rebuild the Docker image **only** when toolchain/dependencies change.

## The 4 types of modifications and where they go

| Need                                 | Where we change it                      |
| ------------------------------------ | --------------------------------------- |
| Vehicle dimensions / specs           | `vehicle/parameters/`                   |
| Controller tuning / gains            | YAML / param files first                |
| New controller / planner             | `src/our_packages/our_controller/`      |
| Modify official Autoware algorithm   | Our fork under `src/` (e.g. `universe`) |
| Custom hardware topics / protocols   | `src/our_packages/our_vehicle_interface/` |
| CAN / serial / UDP bridge            | `src/our_packages/our_bridge/`          |
| New ROS messages / interfaces        | `src/our_packages/our_msgs/`            |
| Launch files / topic wiring          | `vehicle/launch/`                       |
| Vehicle physical simulation          | `simulator/AWSIM/`                      |
| Maps                                 | `data/maps/`                            |
| ROS bags / recordings                | `data/bags/`                            |
| ML models                            | `data/models/`                          |
| ROS 2 / CUDA / compiler deps         | `docker/Dockerfile`                     |

### 1. Vehicle parameters (no code changes)

Keep dimensions, limits, and tunables as YAML parameter files:

```
vehicle/parameters/
├── vehicle_info.param.yaml
├── controller.param.yaml
├── steering.param.yaml
└── acceleration.param.yaml
```

Autoware nodes read these via ROS 2 parameter mechanism — no C++ changes needed.

### 2. Custom hardware topics (new package, no fork)

```
src/our_packages/our_vehicle_interface/
```

Architecture:

```
AUTOWARE                         OUR VEHICLE
────────                         ──────────
/control/command/control_cmd ──→ our_vehicle_interface ──→ /our_robot/motor_cmd
                                                          /our_robot/servo_cmd

/vehicle/status/velocity     ←── our_vehicle_interface ←── /our_robot/wheel_speed
/vehicle/status/steering     ←──                          /our_robot/steering
```

This isolates all hardware-specific translation in one package.

### 3. Replacing control/planning (new package)

```
src/our_packages/our_controller/
├── src/
├── include/
├── config/
├── launch/
├── CMakeLists.txt
└── package.xml
```

Wire it in via launch configuration instead of the stock controller:

```
planner → our_controller → vehicle
```

### 4. Modifying official Autoware internals (our fork)

When we must change an official package's internals, edit it directly under `src/` and track the change in our Git fork.

## Multi-repository manifest

We maintain our own `.repos` file to pin exact versions and mix upstream with our forks:

```
repositories/our_autoware.repos
```

```yaml

  autoware_universe:
    type: git
    url: git@github.com:our-org/autoware_universe.git

    type: git

    type: git
    url: git@github.com:our-org/our_controller.git

    version: main
```

```bash

```

## Git strategy

```
upstream Autoware
       │
       ▼
our fork
       │
       ├── main              ← tracks upstream
       │
       └── research-control  ← our changes
```

For each official repo we modify:

```bash
cd src/universe
git remote -v
# origin    github.com:our-org/autoware_universe.git
# upstream  github.com:autowarefoundation/autoware_universe.git

# create research branch
git checkout -b research-control

# ... make changes ...
git add .
git commit -m "Implement custom vehicle control model"

# keep in sync with upstream
git fetch upstream
git merge upstream/main   # or rebase
```

## Daily development workflow

### Enter the container

```bash
cd ~/av_project
docker compose up -d        # or docker run with bind mount
docker compose exec dev bash
```

### Build only what changed

```bash
cd /workspace/autoware

# Build a single custom package
colcon build --symlink-install --packages-select our_controller

# Build a single modified official package
colcon build --symlink-install --packages-select autoware_mpc_lateral_controller

# Build a package and everything that depends on it (interface/message changes)
colcon build --symlink-install --packages-above our_msgs
```

| Changed what                         | Build command               |
| ------------------------------------ | --------------------------- |
| Implementation only (.cpp)           | `--packages-select <pkg>`   |
| Interface / headers / messages       | `--packages-above <pkg>`    |
| Everything (first time / big rebase) | `colcon build --symlink-install` (no filter) |

### Source and test

```bash
source install/setup.bash

# launch
ros2 launch our_controller our_controller.launch.xml
```

### Docker is NOT rebuilt

Unless we add a new system dependency, change the ROS 2 version, or update CUDA.

## Simulator vs Autoware — the boundary

```
             AUTOWARE
                 │
         acceleration command
         steering command
                 │
                 ▼
              AWSIM
                 │
         VEHICLE PHYSICS
                 │
       ┌─────────┼─────────┐
       │         │         │
     mass    suspension  wheels
       │       friction    etc.
       ▼
 simulated vehicle movement
```

- **Autoware** = autonomous driving algorithms (planning, control, perception)
- **AWSIM / simulator** = physical vehicle dynamics (mass, inertia, tires, suspension)
- Keep them in separate directories: `autoware/` vs `simulator/`

## Platform notes

- **Host OS:** Linux (Jetson / Tegra, ARM64)
- **ROS 2 distro:** humble (or later, per Autoware compatibility)
- **Build system:** colcon with `--symlink-install` for fast edit-test cycles
- **Container runtime:** Docker with NVIDIA container toolkit for GPU access
